# UES 可视化报告统一规范

本文件是 UES 专家套件及所有专项可视化报告的唯一样式、信息架构和组件合同。它只约束呈现，不改变任何专项的准则、证据门槛、严重度或计分公式。

生成 HTML 报告时，优先从 `../assets/report-kit/` 复制模板、CSS 和交互脚本；最终交付可以内联 CSS/JS，保证报告作为单文件打开。专项自己的 `references/visual-report.md` 只补充专项内容，不得重新定义全局壳层、颜色、卡片或证据交互。最新外观与明细交互以 [dashboard-report.md](dashboard-report.md) 为准；随专项分发的共享规范和资源为同版副本，确保单项报告可独立生成。

## 统一术语

| 对象 | 报告显示名称 | 说明 |
|---|---|---|
| 套件加权结果 | UES综合分 / 简易 UES 综合分（依实际口径） | 易用性、任务、一致性与正式或简易性能均有0–10分时显示；简易性能参与时保留来源和限制；基线独立，不进入加权 |
| `ues-baseline-gate` | 基础体验与风险检查 | 显示实证缺陷、验证完整性和覆盖，无数值分 |
| `ease-of-use-suite-47` | 易用性 | 显示基准分；场景参考分单独标注 |
| `task-experience-score` 简易模式 | 简易任务分 | 不冒充真实用户完成率 |
| `consistency-suite-22` | 一致性 | 原始分、风险上限和最终分必须同时可追溯 |
| 合成或单次 PCP | 简易性能分 | 同时显示“单次合成 PCP”或“Reporter 单次实测”来源标签 |
| 非控制台单次网页性能诊断 | 简易性能分 | 显示完成规则、耗时、样本数、缓存状态与限制，不使用 PCP 名称 |
| 正式监控聚合 PCP | 正式线上性能分 | 显示窗口、聚合方式和样本口径 |
| `virtual-user-walkthrough` | 多虚拟用户走查 | 不生成总分，显示角色差异证据 |

不得把“简易性能分”简写为“页面性能”，也不得把单次合成值写成正式线上性能。结构化专项结果可保留其算法规定的正式结果名，联合视图使用上表显示名。

## 页面壳层

所有报告使用同一个三层结构：

1. Hero：报告名、一句话结论、产品阶段、视口/证据等级、评估日期。
2. 三个主标签页：`总览`、`整改优先级 · N`、`范围与方法`。
3. Footer：报告版本与真实存在的 Markdown/JSON/CSV 文件链接。

专项报告即使内容较少，也保持这三个标签页。禁止新增独立“证据图库”页；证据跟随问题、任务或测量结论出现。

首屏顺序固定为：

1. 简易 UES 综合分（仅联合报告且满足计算条件时）；
2. 专项结论仪表；
3. 专项横向对比或当前专项分解；
4. 关键测量/任务摘要；
5. 基线与覆盖。

总览不展开完整问题列表。所有问题统一放在“整改优先级”标签页中，并按独立根因去重。

## 样式令牌

使用 `assets/report-kit/ues-report.css` 中的变量，不在专项中另起一套配色。

- 页面背景 `--ues-bg`，主表面 `--ues-surface`，次表面 `--ues-surface-2`；
- 正文 `--ues-text`，辅助文字 `--ues-muted`，边线 `--ues-line`；
- 主色 `--ues-blue`；通过 `--ues-green`；需关注 `--ues-amber`；失败/门槛 `--ues-red`；
- 页面最大宽度 1680px；卡片圆角 8–12px；Hero 使用蓝色通栏；
- 使用系统无衬线字体；数值使用 tabular numbers；
- 固定使用浅色主题，不以颜色作为唯一状态编码。

总览可使用同一0–10尺度的雷达图辅助比较已评分维度，并附精确数值；不得把缺失维度补成0或连接成完整多边形。默认使用横条以便精确比较。允许蓝色页头和轻量分数卡渐变。覆盖使用分段条和数量。

## 核心组件

### 综合分卡

联合报告满足总分条件时显示：

- `简易 UES 综合分 S / 10`；
- 四个专项的分数、权重和贡献值；
- 完整算式与四舍五入结果；
- 独立的基线状态标签。

基础检查包含无障碍结果，不以日常全局“通过/不通过”否定总分。分别列实证缺陷和未验证项；事前发布规则产生的阻断须另行披露。

### 专项分卡

每张卡只有四层：显示名称、分数/状态、单位、评级与口径。未评分写“未评分 + 原因”，不用短横线或0分。

### 问题卡

每个独立问题使用同一组件，包含：

- 优先级；
- `专项 · 维度 · 准则ID` 标签；
- “对象 + 缺陷 + 后果”标题；
- 一句事实与影响；
- 验收标准；
- 当前问题的截图/状态轨迹/DOM/日志证据。

同一根因命中多个专项或准则时只显示一张问题卡，标签列出全部来源。问题卡不得只给建议而没有证据，也不得把证据放到另一页让读者自行匹配。

### 证据图与灯箱

- 桌面端单张问题证据图使用 280–360px 自适应宽度；两张对比图各不小于220px；窄屏占满卡片宽度。
- 默认保留页面语境；标注层使用红框和问题ID，只用于定位。
- 所有问题证据图支持双击查看原图；键盘 `Enter`/`Space` 等价打开。
- 灯箱占满视口，图片按原比例适配，显示准确替代文本；`Esc`、关闭按钮和点击遮罩均可退出。
- 动态事实同时显示时间戳、轨迹或日志；截图本身不冒充持续时间证据。

### 任务与测量组件

任务路径使用 `入口 → 操作 → 反馈 → 结果 → 恢复` 的紧凑步骤链。性能电影条使用 `前一未完成帧 → 首个完成帧 → 稳定确认帧`，在相同尺度中显示时间戳、完成规则、样本数和误差。

### 覆盖组件

基线与准则覆盖用横向分段条和直接数量表达。`pass`、`fail`、`证据不足`、`N/A` 分开；未验证范围使用清单，不并入通过率。

### 完整准则审计组件

“范围与方法”必须让用户查看当前已执行专项的所有规范准则，不能只展示问题项或汇总数。使用专项切换、状态筛选、ID/名称搜索和完整表格：

- 每条显示准则ID、正式名称、判断状态、证据摘要与必要的范围/重要性元数据；
- 状态至少区分“通过、部分通过、失败、证据不足、不适用/N/A”，不用“有问题”合并部分通过与失败；
- 基线展示全部21条；易用性展示全部47条；一致性展示全部22条；
- 简易任务展示全部20条，并按每个已评任务分别保留判断，不能把不同任务的状态压成一个误导性的汇总；
- 性能展示完整测量合同与公式字段；虚拟用户展示全部计划/运行及其证据状态，它们没有固定准则库时不伪造准则行；
- 筛选只改变当前显示，不删除结构化结果中的记录；默认进入专项时显示其全部条目。

若旧结果没有保存某条准则的独立证据摘要，如实显示“本次产物未单独保存逐条证据摘要”，不得补造证据。下一次评估必须在结构化结果中保留逐条证据，供表格直接读取。

## 专项内容插槽

| 专项 | 总览专属组件 | 范围与方法专属内容 |
|---|---|---|
| 基线 | 四态覆盖、问题与验证完整性 | 21条检查、未验证原因和可选发布规则 |
| 易用性 | 三维分数、基准/场景参考 | page/flow覆盖、权重画像 |
| 一致性 | 原始分→风险上限→最终分 | 比较组、基准类型、22条覆盖 |
| 简易任务 | T1–Tn任务卡与路径 | 任务合同、正常/边界/恢复场景 |
| 简易性能 | PCP电影条、分数与评级 | 来源、口径、样本、误差、公式 |
| 多虚拟用户 | 角色×任务结果矩阵 | 七维画像、运行模式、真人待验证项 |

专项内容进入这些插槽，不改变全局组件结构。

## 响应式与可访问性

- 900px以下：双列分卡、内容单列、问题证据纵向排列。
- 560px以下：所有分卡与公式贡献卡单列；标签导航保持可见且不产生横向溢出。
- 标签页使用 `role=tablist/tab/tabpanel` 与 `aria-selected`。
- 可交互图片有可见焦点和准确 `aria-label`；状态不能只靠颜色。
- 固定 `color-scheme: light`，不跟随系统暗色偏好；动画保持轻量并避免影响阅读。

## 交付与校验

1. 视图只读取已经校验的结构化结果，不在 HTML 中重新估分。
2. 报告中的问题数量、分数、来源和证据路径必须与 JSON 一致。
3. 至少检查桌面1440px、移动390px、三个标签页、问题数、每个问题的证据，以及灯箱打开/关闭。
4. 检查移动端无横向溢出，所有本地链接和图片存在。
5. 联合报告运行 `validate_suite_report.mjs`；专项继续运行各自校验脚本。

用户指定其他格式或已有品牌设计系统时，可以调整视觉外观，但信息层级、术语、证据绑定、风险披露和可访问性交互仍保持一致。

## v0.3 独立检查展示

当前日常检查以“基础体验与风险检查”命名，禁止出现笼统的“基线不通过”主结论。逐条pass/fail/not_verified/N/A保留，not_verified中文为“未验证”，范围外另列，绝不并入失败。全局findings_status和verification_status分开显示；如无事前发布规则，发布状态为“未评估”，不作发布许可推断。

无障碍归入基础体验与风险检查BL-04，可展开细项；不生成独立分数、卡片或专项。

## 渐进展开与明细布局（v0.3.2）

联合 HTML 报告采用以下默认呈现；用户指定其他布局时服从用户。数字、角色数、任务数从当前结果生成，不能照抄示例。

- 整改页使用紧凑问题索引与单个选中问题详情；优先显示事实、影响及建议。验收、准则来源、原始数据按需展开。同一问题的多张证据可切换，保留键盘灯箱、标注开关、筛选与无结果恢复。
- “范围与方法”按内容分为评估范围、多虚拟用户走查、任务轨迹与计分、性能测量、完整准则审计等一级折叠块，默认收起；未执行的内容按实际状态说明。各块复用同一标题样式，字号、字重、文字与箭头起点、内边距一致，不因专项不同混用卡片样式。
- 评估范围展开后：范围字段与证据覆盖分组呈现，桌面双列、窄屏单列；限制说明单独一条。公式、权重明细和去重规则放在二级折叠中，仍可完整追溯，不堆成长段落。
- 多虚拟用户整块收起；展开后按画像切换，只显示当前画像的分配任务。保留任务结果，轨迹与证据继续按需展开。假设画像、共享会话、DOM辅助等限制不能因折叠而省略。无虚拟用户运行时不伪造内容。
- T1–Tn 的轨迹与计分归入同一个任务折叠块，块内任务分别展开；每个任务判断与原始计分仍独立保存。
- 无障碍细项只嵌入完整准则审计的基础检查 BL-04 行内，默认收起。不得再放成同级独立区块；不重复计入顶层准则数，不单独计分。筛选统计只计顶层准则行。
- 从总览点击详情时切到对应标签页，并展开、定位目标折叠块；不要让用户进入新页后再找一遍。

资源：复制 `assets/report-kit/detail-layout.css` 与 `detail-layout.js` 并保留壳层引用；`method-layout-example.html` 演示折叠与范围分组合同。现有报告的内容数量应自行适配，不能用展示示例代替实测数据。

交付前检查：默认折叠状态、画像/问题切换、任务分组、BL-04父行归属；桌面与390px窄屏无页面横向溢出。核对所有一级折叠标题的计算字号、字重、左起点与内边距相同，并验证键盘展开及证据访问。结构化结果校验通过不能替代呈现检查。

明细交互绑定：问题索引用 `data-issue-choice="ID"`、`data-query`、`data-priority`，详情用 `data-issue-detail="ID"`；配套控件 ID 为 `issue-query`、`issue-priority`、`issue-reset`、`issue-empty`、`issue-results`。画像用 `data-persona-choice` / `data-persona-panel`，证据切换用 `data-proof-choice` / `data-proof`，标注开关用 `data-annotation-toggle`。按钮带 `aria-pressed` 与 `aria-controls`，首项选中，其余面板初始 hidden。总览跳转使用 `data-ues-method-target="目标元素ID"`。缺少对应组件时脚本跳过初始化。
