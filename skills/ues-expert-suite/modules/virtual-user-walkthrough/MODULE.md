# UES 多虚拟用户任务走查

七维是角色底座，多用户是运行方式，任务走查是核心能力。输出“什么角色在什么任务中受到怎样的影响”，而不是多人扮演UX专家发表评论。

## 联合运行接口

独立运行继续使用本专项现有plan/assessment合同。由 `ues-expert-suite` 编排时，读取总控的输入/画像/路由版本、任务范围和共享 `evidence-index.json`。本专项现有evidence数组可先作为专项fragment；总控分配或复用全局证据ID后，run、step、rule_observation和issue统一引用该ID。画像冻结、独立会话、动作事实与角色解释仍由本专项合同约束，共享证据不把scenario升级为runtime，也不把角色解释变成真实用户事实。只回写本专项产物和状态片段；画像、任务或证据版本变化时先标stale，不改变七维22细项和无总分边界。

画像与走查观察可以为开放诊断提供候选，但必须把角色假设、工具实测和产品事实分开。读取 `diagnosis.json` 后只复用场景、证据与已检查解释；不得用模拟角色反应把pending候选升级为confirmed，也不得为了不同角色重复执行相同且证据充分的路径。

现有易用性、一致性、任务分等Skill是UES的标准化专家能力。本Skill新增角色化体验证据，不再建立一套通用专家、人格评分或用户满意度总分。

## 读取路由

- 构建、导入或调整角色前，完整读取 [references/persona-model.md](references/persona-model.md)。
- 执行实际走查、截图推演或日志复盘前，完整读取 [references/execution.md](references/execution.md)。
- 保存计划和结果时，读取 [references/data-contract.md](references/data-contract.md)；[assets/example-plan.json](assets/example-plan.json) 是虚构的结构示例，不是已执行记录。
- 汇总报告或联合专家评估时，读取 [references/report-and-integration.md](references/report-and-integration.md)。
- 用户要求验证方法效果、对照实验或论文依据时，读取 [references/method-validation.md](references/method-validation.md)。

## 基本边界

1. 默认使用多个具有任务相关差异的角色。小规模起步通常推荐3个角色、1–3个核心任务；这不是论文证明的最优人数，也不要求穷举七维组合。尊重用户指定的人数、画像和任务；仅1个角色时标明“单角色受限走查”。
2. 每个角色在执行前建立角色属性、技能能力、操作习惯、目标导向、情绪认知、反馈表达、随机行为七维22细项；知识边界单独保存。假设画像主动补全自洽的模拟设定并标注来源，不能用大量未知字段代替构建。区别须落到可观察的选择、理解、求助或恢复规则，不能仅改变语气。
3. 用户群用于发现风险假设，不是对真实人口的抽样。模拟运行结果不得换算成真实完成率、流失率、满意度或人类耗时。
4. 角色只收到目标、必要背景和可见界面，不收到专家准则、其他角色的发现、正确路径或验证侧的隐藏真值。
5. 角色中的“管理员”“愿意冒险”等描述不是实际操作授权。测试账号、状态重置、最终提交、上传、外发、付费、删除或权限变更仍受用户授权和环境限制。

## 1. 确定输入与运行模式

| 材料与能力 | 模式 | 能声称什么 |
|---|---|---|
| 可控制的网页或可运行Demo | `runtime` 实际走查 | 实际发生的动作、反馈、终态；受阻时明确受限 |
| 截图、设计稿、PRD或不可交互原型 | `scenario` 场景推演 | 可见事实及角色风险假设；不能声称点击、完成或放弃已发生 |
| 现有操作日志、录像记录 | `replay` 记录复盘 | 原记录中已发生的行为；不能把多种角色解读当成多个真实会话 |

只有URL但没有浏览器控制能力时，不自动降级并冒称实测。先说明能力缺口；有可见材料则按推演继续，没有材料则交付待执行计划。

只有角色构建需求时停在画像与任务分配，不自动访问或操作产品。混合材料按每次run分别标模式，不把一项实测升级为整个评估已实测。

## 自定义角色入口

用户可以用自然语言、列表或表格提供一个或多个角色，仅填写职能角色、专业背景、工作年限、MBTI等部分信息即可。保留用户设定，按本次任务自动补齐其余字段，输出完整七维角色卡并区分用户提供与模拟补全。具体补全与冲突处理见 [references/persona-model.md](references/persona-model.md) 的“用户提供角色种子”章节。用户已给角色时不擅自替换成预设用户群或增加人数；仅要求捏角色时不自动走查。

开始时简要回显本次阶段（仅画像／仅走查／画像后走查）、交付格式、计划运行数与停止条件。预计耗时不是硬性截止；未获允许不得因时间目标自行删减角色。格式与范围冲突先按用户明确的优先级处理，无法消解且会改变交付时只询问该冲突，可继续不受影响的画像工作。实际走查前依执行协议做入口与任务匹配预检，不能把材料错配算作角色失败。

## 2. 建立计划

记录产品/版本、材料来源、用户群依据、核心任务、任务—角色分配、初始条件、可见渠道、每次动作预算和授权范围。

- 优先保留用户提供的画像与任务。材料充分且操作安全时，可说明假设后继续，不强加逐字段确认。
- 缺失信息会改变业务目标、成功结果或操作权限时，集中询问必要问题；等待期间可完成只读画像草案。
- 核心共享任务用于角色比较；专属任务按职责分配。明确不适用的组合记录理由，不能等失败后再剔除。
- 成功验证规则归评估侧保存。角色可知道业务目标及合理验收要求，但不拿实现步骤、测试答案或隐藏配置。
- 分开列出自然走查与边界/恢复探查。没有自然遇到错误时，不能强令角色犯错并冒称自然行为；可在授权测试环境单列受控探查。
- 采用独立会话、独立数据对象，或在授权范围内恢复相同起点。无法隔离时标为比较受限，不声称后续角色都是首次使用。

执行前保存并校验 `plan.json`：完整画像、情境、行为规则与任务分配使用数据合同0.2.0，冻结 `persona_plan` 并保留原文件。仅构建画像可交付draft；记录正式run前必须frozen。不允许走查后追补画像冒充事前约束。将计划与推断回显。角色或任务的实质变化生成新版本；不要把调整后的运行混入旧计划的同组对照。

## 3. 执行用户群

每个角色—任务—场景—重复次数组合有唯一run ID。给执行者从冻结画像提取的最小角色包（本次情境、知识边界、相关行为规则），分别保存记忆和证据。每个run引用画像版本，规则未触发不强造动作。

多用户不等于必须多进程或多Agent。仅在环境提供且允许时使用隔离执行者；否则顺序运行，并如实标记上下文隔离限制。此Skill不要求创建新的用户可见任务，也不假定存在任何特定浏览器或Agent工具。

执行循环：观察当前状态 → 按角色约束选择合理动作 → 实际操作或明确推演 → 记录反馈与证据 → 判断是否继续。

- 只保留简短的可核对动作说明，不要求或伪造内在思维链、情绪实测或心理独白。
- 模型“扮演不知道”不等于真实遗忘。记录知识约束偏离，不把一次成功当成人类新手一定能完成。
- 达到目标、达到已声明预算、无法安全推进、需要新授权或工具不可用时结束当前run；可继续不受影响的其他安全任务。
- 工具未点击成功、登录受阻、实际产品故障、角色未理解和权限停止必须区分；不一律算产品失败。
- 不因预期某类用户会失败而伪造错误路径，也不为完成任务偷用源码、接口或其他角色答案。

每次运行结束记录任务相关行为规则的触发情况及步骤证据，具体字段见数据合同的 `rule_observations`。未触发或无法判断的规则不作角色差异证据；规则被触发也不等于角色遵循，偏离仍需记录。

## 4. 核验与汇总

验证侧独立核对终态和成功证据。“点击成功”“看到成功toast”不能替代任务要求的对象、范围、保存状态或业务结果验证。

保留三层：可观察事实、角色关联解释、待验证的人类影响假设。报告的完成、错误、停止等结论必须能回到具体run和证据。

按直接原因、对象、用户后果与可共同修复性合并问题，并保留全部出现记录。多人报告同一现象不是多个独立缺陷，也不会自动提高严重度。没有走到问题位置的角色不能记为“未受影响”。

## 5. 交付与专家对接

默认交付可直接浏览的 `report.html`、`personas.html`，同时保留 `report.md`、`personas.md` 和 `assessment.json`，证据按实际可用格式保存到 `evidence/`。每条证据化发现默认配至少一张能直接定位事实的产品截图；报告默认同时提供未改动原图和问题标注视图，标注视图用红框与issue编号指向问题区域，且不得覆盖、改写或冒充原始证据。若事实属于持续时间、先后顺序或瞬时状态，截图需与日志、时间戳或录像证据配对，并明确静态截图不能单独证明的部分。仅要求计划或角色构建时交付 `plan.json`、`personas.html` 和 `personas.md`；不创建虚假run或空报告。用户指定格式时遵从。

报告包含：范围与证据等级、七维用户群摘要、任务结果矩阵、共性/特定角色卡点、证据定位、模型或工具限制、待真人验证项。交付前读取 [references/visual-report.md](references/visual-report.md)，报告使用 UES 统一三标签壳层、路径卡和证据灯箱；配套角色页每维先展示人物描述，再按需展开22项细项与依据，支持角色切换、设定依据展开与对比。复用本Skill的可视化组件，完整规则见该参考。用户只要Markdown或其他格式时遵从，不额外强制HTML。

联合评估属于用户当前范围且对应专家Skill可用时，读取它们的现行指令并传递证据；否则只输出待交接包，不假装已完成专家评分。任务分Skill的任务确认门、覆盖要求与算法保持原样；本Skill的计划采用不等于任务分已获确认。

不生成虚拟用户总分，不平均角色主观评分，不自行改动其他Skill权重。跨专家结论保留来源和独立分数，不把重复问题再叠加扣分。

保存结构化输出后运行：

```bash
python3 scripts/validate_assessment.py /absolute/path/to/assessment.json
```

只有计划时同样校验 `plan.json`。脚本检查字段、模式、引用、证据链与输出边界，不证明浏览器确实运行、画像忠实或问题真实；这些仍需回看原始证据核验。

### 触发与行为分别验收

新运行的rule_observations同时记录触发状态与behavior_check（符合／偏离／证据不足／不适用），分别绑定证据。打开帮助只证明相应入口行为，不自动证明反馈表达或其他规则符合。具体结构见数据合同。新运行交付使用校验器的 `--require-behavior-check`；历史结果不倒填，仅按兼容模式检查并声明未记录的行为判断。

角色结果矩阵同时显示outcome和stop_reason的可读含义，预算停止、产品阻断、无法核验分别展示；不把所有非完成结果统一写“失败”，不把预算内完成差异解读为能力差异。字段不一致按现有合同拒绝，呈现规则见visual-report.md。
