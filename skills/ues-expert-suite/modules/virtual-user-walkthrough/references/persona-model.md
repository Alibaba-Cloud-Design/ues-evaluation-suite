# 七维角色构建：完整画像到执行约束

先构建并保存角色，再执行走查。不能先浏览出一条路径，结束后再补齐角色字段。用户要求简短报告只缩短展示，不降低执行前画像的完整性。

## 七维与22个细项

下表是本Skill的产品走查模型，不冒称论文原始量表。每个角色保留全部细项；知识边界作为单独执行上下文保留。

| 维度 / key | 细项 / fields | 可观察作用 |
|---|---|---|
| 角色属性 `role` | 职能角色 `job_role`、专业背景 `professional_background`、工作年限 `years_experience`、MBTI `mbti`、产品使用阶段 `product_stage` | 职责相关对象、业务语言、首次与再次使用的差别 |
| 技能能力 `skills` | 熟练度 `proficiency`、技术背景 `technical_background`、问题恢复能力 `recovery_ability` | 会做什么、遇错能采取哪些恢复动作 |
| 操作习惯 `operating_habits` | 信息偏好 `information_preference`、使用路径倾向 `path_tendency`、导航偏好 `navigation_preference` | 先查分类还是搜索、看示例还是参数、是否使用可见快捷入口 |
| 目标导向 `goals` | 目标导向强度 `goal_intensity`、容错容忍度 `error_tolerance`、成功感路径 `success_path` | 如何取舍探索与直达、什么结果足以满足需求 |
| 情绪认知 `emotional_cognition` | 认知负荷承受 `cognitive_load`、焦虑敏感度 `anxiety_sensitivity`、决策路径期望 `decision_expectation` | 如何拆分信息、何时核对、继续探索或暂缓判断 |
| 反馈表达 `feedback_expression` | 表达偏好 `expression_preference`、理解偏好 `understanding_preference`、反馈动因 `feedback_motivation` | 求助如何表述、需要示例还是规则、是否愿意反馈 |
| 随机行为 `behavioral_randomness` | 行为类型 `behavior_type`、随机行为设定 `random_behavior` | 合理备选路径、偶发探索及范围 |

## 事实、假设与未知

每个细项记录 `value`、`status`、`basis`、`reason`。status为 `provided`（用户提供）、`evidenced`（材料支持）、`assumed`（模拟设定）、`unknown`、`not_applicable`。basis引用来源索引。

- 假设用户：在用户给定条件内，主动构建具体且自洽的模拟设定。没有访谈不等于不能设定导航偏好、决策取舍或恢复习惯；注明assumed即可，不应把主要维度全部写成未知来凑字段。
- 真实用户复现：优先已有材料，不补造真实经历或心理属性。未知项可保留，并缩小可解释的差异范围。
- MBTI保留为背景字段；未提供时可写未知，不必随机分配。不能从MBTI、年限或职业直接推导操作能力、权限和所有偏好。
- 工作年限和技术背景分别描述；10年设计经验不代表熟悉云控制台。产品熟悉度须明确范围，不凭“老用户”标签补造隐藏入口记忆。
- 情绪认知是预设行为倾向，不是测得的焦虑、满意度或认知负荷。把“对不确定成本敏感”转换成查看费用说明，不表演心理独白。
- 随机性默认采用定性、合理的路径变体。“3%”只能作为有来源或明确标注的实验参数；未实施抽样就不声称运行了3%误操作，不为达成比例强造错误。

## 用户提供角色种子

支持自然语言、列表、表格，以及用户提供的角色卡材料。用户无需先填完整22项，也无需准备JSON。可只给一个或多个角色的姓名/代号、职能角色、专业背景、工作年限、MBTI，或任意其他七维字段；产品经验、需求、偏好等也可直接提供。

- 将明确提供的信息映射到对应字段，原意保留，标 `provided`，basis引用该次输入。用户主动捏的虚拟设定仍是假设画像；“用户提供”仅说明来源，不能称为真人事实或调研证据。
- 已提供字段是补全约束，不为套用新手/专家模板改写；保留用户指定人数。未提供且与模拟相关的字段，结合职责、专业领域、本次产品/任务及明确偏好给出自洽设定，标 `assumed`，解释为何这样设定。背景不足时选择合理默认并披露，不能声称这是对该职业人群的事实推断。
- MBTI仅作为用户指定的背景值保留，不据此自动确定能力、认知负荷、容错、权限或决策方式。工作年限不等于本产品熟练度；同类产品经验也不等于本站经验。缺失MBTI保持未知，其余任务相关维度主动补全。
- 用户明确要求的探索型、谨慎、偏好参数等行为偏好优先使用；没有提供时是独立模拟假设，不包装为MBTI必然推论。各角色差异必须落到实际可观察规则。
- 同一字段有互相冲突的明确值，或缺少信息会改变业务目标/权限时，集中询问必要问题；不要悄悄覆盖。专业经验多但本产品新手可以同时成立，不强行消除。
- 产品或任务尚未给出且只要求构建角色时，交付draft角色卡；context中缺失的任务情境写明待定，行为规则可限于通用可见情境。待任务明确后形成任务相关版本并冻结，不能为补齐情境擅自访问产品。
- 补全后简短回显“保留了哪些输入、补全了哪些设定、哪些仍未知”，并交付可视化角色卡与Markdown；已授权走查时完成计划冻结后继续，不增加逐字段确认。用户明确要求先看角色再走查时停在角色交付。
- 用户后来修改角色时，新信息替换相应草稿值；已冻结或已有run则新建画像/计划版本，保留旧记录，不改写历史。

示例输入：

> 捏一个虚拟角色：Jump，体验设计师，工业设计背景，工作10年，ENTJ。首次使用本产品，想确认它能否帮助制作方案汇报。其余按七维补全，先给我看角色卡。

预期处理：上述信息标为用户提供；导航偏好、恢复方式、目标取舍等补全为模拟设定，说明依据；不从ENTJ断言擅长技术或低容错。生成完整22项、情境和相关行为规则，停在draft角色交付。

## 连贯人物描述与字段一致性

角色构建采用：用户输入 → 七维人物描述 → 22项结构化细项 → 可执行行为规则。七维描述让读者理解这个人如何工作，细项保留可核对来源，规则用于未来观察。不能用一段人物故事代替完整字段，也不要让画像只剩通用操作守则。

- 每维写一个具体主题和一段紧凑描述；连接工作背景、信息选择、目标取舍、反馈与恢复方式，跨维形成自洽人物。例如“先建立结构，再验证结果”可以贯穿分类浏览、案例阅读与结果核对，但不能把这句话固定套给所有角色。
- 具体习惯应能区分人物：先读摘要还是直接试用、遇到不确定性如何处理、在效率和核对之间如何取舍。避免人人都成为细致、理性、总能恢复的理想用户。故事中的习惯和规则均为倾向，不强制每次触发，不预设成败。
- 用户提供的经历保留原意，新增工作习惯、动机与场景标模拟补全。不得无依据添加具体雇主、任职经历、设备、私生活或心理诊断；不能把“长期做设计”扩写成“从未跳槽”，也不能由学历断言精通某技术。
- MBTI可在角色简介保留，但不作为能力、权限或全部偏好的决定依据；模拟人格描述不能冒充真人事实或心理测量。
- 描述中的每个行为主张须与22项字段及相关规则一致。新增有实质作用的习惯要同步更新字段/规则；没有任务时保留通用候选规则，不补造任务或界面路径。
- 七维故事和细项默认放在同一角色页。每维先显示人物主题、描述与简短来源说明，细项及详细依据折叠展开；姓名与用户提供信息保持可见。

可在Persona增加可选 `narrative` 对象保存描述（不是新的第八维）：`summary, status, basis, note, dimensions`。其中 `dimensions` 使用现行七维key，每维含 `title, text, source_note`。混合用户信息与扩写的叙述标为 `assumed` 并引用两类来源；每个细项的原始来源状态不变。当前校验器允许该扩展字段，语义一致性仍需人工核对。

## 从角色卡到执行包

保存三层：

1. **角色卡**：七维22细项及来源，具有稳定ID和版本。
2. **本次情境 `context`**：业务需求 `need`、实际产品经验 `product_experience`、已知概念 `known_concepts`、未知概念 `unknown_concepts`、设备/时间等条件 `conditions`。操作授权仍归任务合同，性格不产生权限。
3. **行为规则 `behavior_rules`**：每条有稳定ID、引用细项 `field_refs`、可见触发条件 `when`、候选动作 `action`、可核对表现 `check`。提取与任务相关的规则，不要求22个细项各造一条动作。

例如同样是“判断功能是否适合需求”：

- 新手偏好具体场景和分类浏览：看见多个功能分类 → 找与业务用途相关的分类并读示例 → 用页面实际文案说明功能能帮助什么，不凭模型知识补齐术语。
- 同类产品使用者偏好直达详情和确认成本：页面提供规格或套餐 → 查看输出格式、限制与计费说明 → 记录哪些条件已知、哪些仍不确定，不预设必须失败。
- 对模糊反馈容忍度低：动作后无可确认结果 → 检查页面提示或帮助，再决定是否继续 → 保存反馈证据；停止不自动解释为真人流失。

规则不包含具体控件位置、正确路径、隐藏真值、预设缺陷或其他角色发现。使用实际存在的工具；喜欢快捷键不允许猜测产品快捷键。反馈表达规则在自然求助/反馈时触发，不授权外发消息。

## 构建与冻结

执行前完成：

1. 保留用户画像条件，按产品实际使用者选角色，不固定为新手/中级/专家。
2. 填好22项及状态，说明各角色新增覆盖。假设角色在操作习惯、目标取舍、恢复/认知倾向上应有具体设定；不相关字段可说明原因后标不适用。
3. 核对自洽性：职业与权限、业务经验与产品经验分开，目标与任务一致；矛盾设定解释情境或修正，不凭标签自动成功或失败。
4. 提取行为规则，核对引用字段和触发情境。字段通过规则使用，或在 `inactive_fields` 说明为何不驱动本轮操作，不能只改变报告语气。
5. 保存 `plan.json`，画像版本、任务分配及规则冻结为 `persona_plan.state=frozen`，简短回显差异和假设后执行；不新增逐字段审批门。

仅构建角色时可交付draft，不自动访问产品。正式run引用 `persona_version`；画像/任务实质变化另建计划版本，不混入原对照。保留执行前plan.json，不用结果覆盖它。

角色可从本run界面学习并记录来源。知识泄漏或规则偏离记录为 `persona_deviation`，限制差异解释，不静默替换历史。共享上下文顺序执行仍须披露隔离限制。冻结标记只能验证声明，不能证明真实时间顺序或模型遗忘。
