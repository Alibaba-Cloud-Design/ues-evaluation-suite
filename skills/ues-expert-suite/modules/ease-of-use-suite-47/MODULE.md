# 易用性评估专家套件

以47条准则发现问题，以可定位证据约束结论，以问题加权扣分制计算基准分，并按已评审场景标签计算可拆分的场景参考分。通过项只证明覆盖，不为总分加分；未知证据不产生满分；问题重要性和缺陷程度用于扣分与建议分级，分数不再附加风险封顶或发布裁决。

## 联合诊断接口

由 `ues-expert-suite` 编排时，先读取已校验的 `diagnosis.json` 与共享证据索引。confirmed候选作为待映射发现，rejected候选用于避免重复误报，pending/blocked不能进入实证缺陷或扣分。本专项仍需按canon逐条证明关联、完成全部适用项查漏并独立判断；已有证据满足当前条目要求时直接引用，只补缺口，不重复走同一路径。

dual模式计算结果中的 `scenario_impacts` 由脚本生成每个问题的基础扣分、场景系数、场景扣分、差值和驱动场景。报告使用该结构解释场景影响，不手工重算，也不把分差大小写成洞察深度。

## 联合运行接口

独立运行继续使用本专项现有合同。由 `ues-expert-suite` 编排时，读取总控冻结的画像、范式确认、任务、输入版本和共享 `evidence-index.json`，优先复用已有页面、状态、截图、DOM与交互ID，避免重复导航和取证。每条判断仍须写明该证据对本准则的具体含义；共享observable_fact不能直接成为pass、partial_pass或fail。新取证先写专项fragment，由总控合并索引；本专项只回写自己的产物和状态片段。依赖版本变化时先标stale并重新执行受影响判断和计分，不改变47条、维度门槛、场景权重或扣分公式。


## 启动场景分析与赋权

开始正式判断前完整读取 [references/scenario-weighting.md](references/scenario-weighting.md)。先预览材料、识别核心任务，推荐本次输入的一个主范式和最多一个辅助范式及评估比例；附三类页面示例，向用户确认一次。两种比例相差不超过20个百分点（含60%/40%）时说明定位接近。用户已明确指定范式与比例时直接记录，不重复询问；回复前不把模型推荐写成用户确认。

两个专项均支持辅助范式。所有任务场景使用同一份已确认范式比例；任务、页面和步骤仍可有多个。将实际用户选择记入 context.paradigm_selection，冻结 context 后调用 scripts/scenario_profile.mjs。两套一起评估时共用一次确认；同范围复测沿用已确认配置。

场景相关性用于检查优先级与参考分，不改变 canon 的适用条件、判断标尺和证据要求。标准模式覆盖所有适用项；任务未命中不能直接 N/A。未完成标签按中性系数回退，已删除或合并的旧项不恢复。

默认 dual，同一份结果计算基准分与场景参考分。等待回复时可继续只读预览与整理任务，不开展依赖范式选择的正式评估；未回复不等于接受推荐。用户明确只要基准评估时可用 baseline，不需要范式确认。基准分用于质量评级；场景分标记“参考分（试行）”，不套用正式档位。

## 准则库

正式评估前完整读取 [references/canon-47.md](references/canon-47.md)。该文件是条目命题、适用条件、重要性和判断标尺的唯一依据。

## 输入能力与报告边界

| 输入 | 可评范围 | 评分名称 |
|---|---|---|
| 单张或无顺序截图 | 可见page条目；易操作性通常只能评价少量静态线索，flow记证据不足 | 静态易用性评分；易操作性局部评分或未评分 |
| 有明确先后关系的多张截图 | page条目 + 由动作前后状态直接支持的flow子判断 | 状态序列易用性评分 |
| 可运行HTML Demo | 必须实际执行核心任务并测试完整版易操作性 | Demo易用性评分，含易操作性实测 |
| 已上线网页URL | 必须使用浏览器实际执行核心任务并测试完整版易操作性 | 完整易用性评分；受登录、权限或数据阻断时为受限URL评估 |

截图评估不得使用“综合易用性已经优秀”等措辞替代范围声明。没有验证flow时，只给静态评分，并明确完整流程尚未评级。

## 易操作性证据规则

先根据输入类型确定证据等级，不得因为已经发现足够多的视觉或文案问题而提前停止易操作性测试。

### HTML Demo或已上线URL：默认必须完整实测

只要页面可运行，就必须使用浏览器完成当前授权和可访问范围内的易操作性测试。不能仅查看截图或DOM后把整个易操作性维度标为“未评分”。

对1–3个核心任务至少验证：

1. 真实入口、对象和作用范围；
2. 正常路径从开始、操作、反馈到结果去向；
3. 至少一个适用边界状态，如空结果、无效输入、不可用条件、失败、重试或取消；
4. 点击后的即时反馈、加载状态和最终状态；
5. 选择、筛选、输入、模式或保存状态是否持续可见；
6. 返回、关闭、取消、重试、撤销或其他适用恢复路径；
7. 页面跳转、弹层和新标签中的对象与位置连续性；
8. 桌面页面适用时检查Tab顺序、焦点可见性、Enter提交和Esc关闭；
9. 局部更新时目标是否移动、内容是否大范围跳动；
10. 高频、批量或跨角色任务适用时检查加速与交接。

遇到新标签、弹窗、跨域页面或浏览器上下文切换时，必须尝试取得目标上下文并继续验证；若第一次自动跳转未被工具捕获，应通过当前标签、目标标签或可见链接重新进入。只有工具确实无法控制目标上下文时，才能记为测试阻断；自动化操作不便既不是产品缺陷，也不是提前结束易操作性测试的理由。

完整版易操作性不是要求穷尽所有角色和后端状态，而是要求每个已冻结核心任务至少走通正常路径，并覆盖一个适用边界状态。安全、只读、可逆的交互应继续测试，直到满足该条件或遇到真实阻断。

登录、权限、缺少测试数据或外部系统确实阻断核心路径时，输出“受限易操作性评分”，并列出阻断点。若至少一个核心任务已完成正常路径和边界路径，仍应对已覆盖范围给出受限易操作性分数，不得因其他分支证据不足而整体放弃评分。只有页面无法运行，或所有核心任务均被真实阻断且不足3个易操作性条目可判断时，才允许输出“易操作性未评分”。

删除、购买、发布、权限变更、生产操作、上传或对外发送等有副作用的最终动作仍需遵守授权边界。可以安全测试其入口、条件说明、确认界面、取消与返回；未经授权的最终提交记证据不足。单个高风险终点未执行，不等于整个易操作性维度无法评分。

### 工具切换与环境约束

切换前核对用户明确的账号、会话隔离、数据对象和操作边界。新工具仍满足这些条件时可直接继续，记录切换及实际起点；不用为工具名称变化再次询问。用户已批准的降级范围可复用，不重复确认。

若新环境不能满足或无法验证用户明确要求的独立会话、存储隔离等条件，应在依赖该条件的正式操作前说明差异并取得放宽授权；期间继续不依赖该条件的材料整理和只读能力检查。空标签、空列表或“任务专属浏览器”不证明底层存储隔离。不能先降级执行、再以末尾限制声明代替授权，也不能将工具受阻记为产品失败。

保留原条件、切换原因、替代环境及已验证/未验证属性、已有授权依据、受影响任务和后续执行范围；可放在既有environment/limitations与报告环境节，不必创建额外产物。只有用户明确要求的约束发生实质变化才需要澄清，不把默认偏好升级为新审批门槛。

### 单张截图：只评价局部静态易操作性

单张截图不能证明点击反馈、加载、提交结果、错误、恢复、焦点或状态转换。只检查截图直接支持的page级易操作线索，例如操作对象与范围、可见输入要求、视口折线和继续线索。

- 达到维度评分门槛时，可输出“局部静态易操作性评分”。
- 未达到门槛时标为“易操作性未评分”。
- 两种情况都不得写成“完整易操作性评分”。
- 不得根据按钮看起来可点，推断点击有效、反馈及时或结果正确。

### 多张截图：先建立状态跳转关系

收到多张截图时，先为每张记录状态编号、当前对象、可见选中状态和时间顺序，再建立：

`起始状态 → 用户动作 → 反馈/中间状态 → 结果状态`

只有满足以下条件的截图组合才能作为flow证据：

- 用户提供了顺序或动作说明，或画面中存在足以唯一确定顺序的连续状态；
- 前后状态属于同一对象和任务；
- 能定位触发动作以及动作后的可见变化；
- 不存在同样合理的其他跳转解释。

互不关联、没有顺序或仅展示不同页面外观的截图，应按多张独立单截图处理，不能虚构跳转关系。

如果证据覆盖了核心路径的开始、动作和结果，可输出“状态序列易操作性评分”；如果还覆盖了反馈、边界和恢复，可进一步提高flow覆盖声明，但多截图仍不等同于可运行Demo或URL的完整实测。

### 易操作性结论名称

报告必须从以下四种名称中选择，并说明依据：

- **完整易操作性实测**：HTML或URL的核心正常路径和至少一个适用边界状态均已验证。
- **受限易操作性实测**：HTML或URL已实际操作，但受登录、权限、数据、外部系统或授权范围限制。
- **状态序列易操作性评分**：多张截图建立了可证实的动作—状态关系。
- **局部静态易操作性评分 / 易操作性未评分**：只有单张截图或无顺序截图。

## 评估模式

- **快速模式**：用户明确要求快速查看时，检查重要性3条目和最明显的可见问题，输出Top 5与静态扣分。
- **标准模式**：默认。检查所有当前适用且可验证的条目，输出严格评分、问题清单、条目表和覆盖声明。
- **严格模式**：用户要求完整审计时，冻结角色、核心任务、环境、边界状态和高风险操作后执行。

优先根据材料推断上下文并继续。只有缺失信息会显著改变任务、风险或适用性时才追问；推断必须写入报告。

## 产品画像

记录：

- 产品范式：narrative、exploration或task_system
- 目标用户：新手、普通用户或专家
- 研发阶段
- 1–3个核心任务
- 页面范式
- 删除、付费、权限、批量处理、生产变更和外发等风险

按真实目标用户评估，但不要因为用户是专家就自动放过产品内部术语。行业通用术语可以接受；产品自造概念、模糊动作和未知缩写仍需解释。

## 条目筛选

1. 按输入证据能力筛选page和flow条目。
2. 条目有“适用条件”或“触发条件”时，仅在条件满足时纳入；明确不满足记not_applicable。
3. 条件是否满足也无法判断时记insufficient_evidence，不要把未知当作N/A。
4. 没有条件字段的条目默认适用。
5. 缺少当前范式权重时按1处理，不代表N/A。
6. 任务范围匹配、范式权重高和重要性高的条目优先执行。

## 证据记录

每条至少记录：

- 条目ID和标题
- 证据方式：screenshot、dom、interaction或content_review
- 证据：区域、可见文案、选择器、状态变化或截图坐标
- 判断：pass、partial_pass、fail、insufficient_evidence或not_applicable
- 置信度：high、medium或low
- 关联根因：如适用

证据要求：

- pass也必须给出依据。
- 对可在界面中定位的失败或部分通过项，保留未改动原始截图，并在报告中默认显示其标注视图：用红框和对应 `issue_id`／问题序号指出问题区域，可切换回原图。标注不得遮挡关键内容、改写产品状态或替代原始证据；同一问题涉及多个区域时使用同号A/B后缀，无法可靠定位时说明原因而不画猜测框。
- 截图没有展示tooltip、hover、展开、确认弹层、提交反馈或终态时，相关交互判断必须记insufficient_evidence。
- 可见证据已经表明关键必要信息缺失、状态冲突、核心动作不明确或高风险范围不清时，可以判fail；不要为了避免严厉而一律降成partial_pass。
- 不得用“通常会有”“后续页面应该说明”替代证据。
- 在线评估默认只读。提交、删除、付费、权限变更、生产操作和对外发送必须先获得明确授权。

## 从条目发现合并为问题

先完成条目判断，再按根因合并问题。每个问题—准则关联都要能独立回答：该准则的具体命题是什么、哪个实际对象/状态违反了它、对应证据在哪里。沿用准则evidence字段记录这些依据，不用关键词相近或同属“连续性”作为关联理由。

同一事实可能同时违反多条准则，但须逐条证明；仅作为影响标签也不免除该要求。例如刷新后对象缺失直接支持保存/结果去向问题，是否还违反空间连续性，要依据实际转换的起点、终点与层级另行判断，不能自动套用，也不能一概禁止跨准则关联。

移除无法成立的关联后，依据该准则剩余证据重新判断：证据不足保留insufficient_evidence，不能自动改pass或N/A。同步覆盖统计、问题条目映射、最高严重度、主要扣分维度与两类分数，重新运行原计分脚本；不直接手改分数。“同根因只扣一次”不代表错误关联不会影响覆盖或严重度。

合并规则：

- 仅当多个发现同时满足“同一直接原因、同一操作对象或界面区域、同一用户后果、可由同一项修改完整修复”时，才合并为一个扣分问题。
- 同一文案风格影响不同核心动作，但可能造成不同业务结果时不得合并。例如“接受”“拒绝”“延后”分别可能造成错误认领、错误丢弃和遗漏处理，应独立计问题。
- 同一根因在同一对象上影响多个准则时只形成一个问题，并列出全部受影响条目。
- 同一问题只选择一个主要扣分维度；其他维度可作为影响标签，不重复扣分。
- 不得把同一位置、同一后果、同一修复的视觉或文案缺陷拆成多个问题重复扣分。
- 不同位置、不同原因、可独立修复的问题可以分别扣分。

合并前做“四问检查”：

1. 原因是否完全相同？
2. 用户是否会在同一对象上遇到？
3. 最坏后果是否相同？
4. 一项修改是否能完整消除所有发现？

任一答案为“否”或证据不足时，保持为独立问题。可以在报告中归入同一主题，但扣分不得因此消失。

## 严格问题优先级

条目严重度仍按准则重要性判定：

| 重要性 | fail | partial_pass |
|:---:|:---:|:---:|
| 3 | High | Major |
| 2 | Major | Minor |
| 1 | Minor | Advisory |

合并后的问题取受影响条目的最高建议严重度。High（高）、Major（较高）、Minor（一般）、Advisory（建议）仅用于扣分、问题排序和整改建议，没有特殊否决身份。对后果的说明须有证据；不得因严重度另行压低总分。

## 问题加权扣分制

下述为基准口径。数字计算读取 [references/scoring-model.md](references/scoring-model.md)，调用 `scripts/calculate_ease_of_use_score.mjs`；dual 模式追加场景参考分与每条问题的权重来源。问题的 `scenario_links` 仅为计分增加准则/场景关系，不要求改造现有证据字段。

### 1. 维度是否可评分

易见性、易学性、易操作性分别判断，不允许把缺少证据的维度默认为10分。

一个维度只有同时满足以下条件才可评分：

- 至少有3个适用条目获得pass、partial_pass或fail判断；
- 当前证据覆盖了该评分名称所声称的范围；
- 该维度中证据不足的条目不超过“已判断 + 证据不足”的40%。

以上数量与比例只统计评分名称所声明的范围。例如“静态易用性评分”只统计page条目；未验证的flow条目进入总体覆盖声明，但不混入静态维度的证据阈值。

输入类型还必须满足：

- HTML Demo或URL存在安全可操作路径时，必须继续测试，不能把尚未尝试的交互直接计入40%证据不足并据此放弃易操作性评分。
- HTML Demo或URL完成至少一个核心任务的正常路径与适用边界后，可对已覆盖范围评分；其他真实阻断进入受限声明。
- 多张截图只有在状态图至少包含起始状态、触发动作和结果状态时，flow证据才能参与易操作性评分。
- 单张截图只能形成局部静态易操作性评分，不能用page通过项替代完整flow证据。

未满足条件时标为“未评分”，写明原因，不进入算术平均。少于2个维度可评分时，不输出数值总分，只输出问题级别、整改建议和覆盖声明。

截图中的page证据可以形成“静态易见性”或“静态易学性”；不得因为少量可见控件位置合理，就把依赖点击反馈、提交结果、撤销和异常路径的完整易操作性评为10分。

### 2. 维度扣分

每个可评分维度从10分开始，按问题的主要维度扣分：

- 每个High问题：扣3分
- 每个Major问题：扣1.5分
- 每个Minor问题：扣0.75分
- 每个Advisory问题：扣0.25分
- 每个维度最低0分

通过项不增加分数。insufficient_evidence和not_applicable不直接扣分，但前者会影响维度是否可评分和覆盖声明。

### 3. 汇总分数

总分为全部可评分维度的算术平均，保留一位小数；最终分等于汇总分，不做二次风险封顶。基准分与场景参考分分别汇总，0–10 的量表范围不变。

### 4. 评级

- `[0, 5)`：差
- `[5, 7)`：中
- `[7, 8.5)`：优
- `[8.5, 10]`：卓越

边界按左闭右开执行，10分包含在“卓越”内。例如4.9为差、5.0为中、6.9为中、7.0为优、8.4为优、8.5为卓越。

评级只描述已验证范围的质量；证据覆盖不足仍应标受限评估。报告不给自动发布裁决。

## 覆盖与评分约束

分别报告：

- page：适用数、已评分数、证据不足数、N/A数
- flow：适用或疑似适用数、已验证数、证据不足数、N/A数
- 总体：已验证数 / 适用或疑似适用数

规则：

- 单张截图没有flow证据是正常限制，不降低静态评分，但禁止输出完整流程评级。
- 多张截图必须先报告已证实的状态跳转图；没有跳转关系时按独立单截图处理。
- 证据不足不得以任何形式换算为通过或10分；它通过“维度未评分”和覆盖声明影响结论可信范围。
- 如果截图裁切、模糊或状态缺失导致超过20%的适用page条目证据不足，只输出“暂定静态评分”，不得给确定评级。
- URL或Demo必须主动测试易操作性；只有在核心任务正常路径和至少一个适用边界状态被验证后，才可以输出“完整易操作性实测”和完整易用性评级。
- URL或Demo受真实阻断时输出受限评估，并明确已经实际完成的任务、未完成的任务和阻断原因；不得笼统写“易操作性未评分”。
- 覆盖率不得参与加分，也不得被藏在报告末尾。
- 输出质量评级、问题严重级别、整改建议与覆盖限制，不生成发布通过、不通过或复审结论。

## 报告交付形态

标准模式和严格模式默认输出“双层报告”：

1. **可视化主报告**：让决策者快速看清结论、分数来源、核心任务路径、问题优先级和证据覆盖。
2. **审计明细**：保留逐项判断、可定位证据、扣分算式、测试路径、限制与47条准则明细，供设计、研发和复审追溯。

两层必须来自同一份评估数据，禁止分别估分或为了图表效果调整严重度、覆盖率和质量评价。可视化是信息组织方式，不是另一套评分算法。

当运行环境提供会话内可视化能力时，标准模式和严格模式必须完整读取并遵守 [references/visual-report.md](references/visual-report.md)，生成使用 UES 统一三标签壳层、组件和证据灯箱的可交互主报告；除非用户明确要求纯文字。快速模式在用户要求“可视化”“看板”或“图形化”时使用同一规范的精简版。

当可视化能力不可用或输出载体不支持时，回退为结构化Markdown报告，并明确说明未生成可视化；不得因此省略任何审计内容。纯截图且证据不足时也可以生成可视化，但必须把未评分、未知和流程未验证直接呈现，禁止用空白图表、默认满分或推测数据补齐。

## 报告内容结构

无论采用可视化还是Markdown，标准模式都必须包含以下内容；可视化中的标签页、筛选和展开项可以承载这些信息，不要求按同样的纵向顺序重复展示。

### 1. 评估摘要

- 评分名称：静态 / 状态序列 / Demo / 完整
- 原始分：X.X / 10，或因证据不足不评分
- 最终分：X.X / 10，或因证据不足不评分
- 评级：差 / 中 / 优 / 卓越
- 整改摘要：最重要问题、建议优先级与未验证范围
- 核心结论
- page覆盖与flow覆盖

### 2. 各维度评分

- 易见性：X.X / 10或未评分
- 易学性：X.X / 10或未评分
- 易操作性：X.X / 10或未评分

每个可评分维度列出扣分算式，例如：10 - 3（High）- 0.75（Minor）= 6.25。未评分维度列出已判断数、证据不足数和未达到的评分条件。

### 3. 易操作性测试记录

- 证据等级：完整实测 / 受限实测 / 状态序列 / 局部静态 / 未评分
- 核心任务与真实入口
- 已测试正常路径：动作 → 反馈 → 结果
- 已测试边界状态与恢复路径
- 键盘、焦点、局部更新和跨页连续性结果
- 未测试路径、真实阻断和授权边界

HTML Demo和URL报告必须包含本节。多张截图报告必须在本节列出已证实的状态跳转关系。单张截图只需说明可评的局部静态条目和flow证据不足。

### 4. 优先问题

每个问题包含：

- 问题标题与High/Major/Minor/Advisory级别
- 主要扣分维度
- 影响条目
- 可定位证据
- 至少一张实测问题截图；默认同时提供未改动原图和红框编号标注视图，并允许查看原图；若客观不可截图，写明原因并提供可复核的非视觉证据
- 对核心任务的影响
- 明确的修改对象、位置、文案或交互建议
- 修改后的预期改善

可视化主报告中的每个问题必须支持单独导出 Markdown 与 JSON，并提供全部问题 CSV 或 JSON 导出；导出字段、截图引用和报告正文必须来自同一份结构化结果。

### 5. 条目判断表

列出所有适用page条目；URL、Demo或状态序列评估还应列出实际检查的flow条目。表格至少包含ID、判断、置信度和证据摘要。

### 6. 覆盖与限制

明确列出insufficient_evidence、not_applicable、未测试角色、状态、权限和高风险操作。截图报告必须写明“本分数仅代表可见静态状态，不代表完整流程质量”。

同时说明哪些维度因证据不足未评分。不得把“未评分”写成“未发现问题”。

## 建议质量

建议必须能由设计、前端或文案直接执行，并说明改动边界。避免“优化体验”“增强可读性”“完善交互”等空泛表述。

## 边界

- 本套件不等同于无障碍合规、安全审计、完整视觉质量或设计系统审计。
- 不做竞品结论，除非用户另行提供竞品和比较任务。
- 单一URL不保证覆盖全部角色、异常状态和后端真实结果。

## 场景结果的报告补充

在现有摘要中呈现场景/任务、计分模式、基准分、场景参考分与差值；在审计中保留 profile_id、策略版本、权重来源与中性回退。场景分未评分时显示原因；不得替代原覆盖声明，不作自动发布裁决。现有取证、截图、证据字段与导出约定继续使用。
