# 场景拆解与赋权（v2，主辅范式确认）

正式评估开始时读取本文。检查项与判断标尺继续使用当前 canon；本文只扩展启动分析、检查优先级和数字计分，不替换原有取证、证据字段与导出约定。

## 启动分析与一次确认

一次输入最多选择一个主范式和一个辅助范式，两套专项都支持辅助范式；这是本次整体评估的定位，不是限制只能检查两个任务或页面。产品类型仅提供理解线索。模型先只读预览材料，识别用户角色、1–3个核心任务和实际场景，给出建议范式、比例及依据，默认向用户确认一次。

使用以下名称和示例解释范式，避免只抛出抽象标签：

| 范式 | 页面示例 | 关注目标 |
|---|---|---|
| 展示叙事型 `narrative` | 营销落地页、AirPods 产品官网、公司官网 | 阅读、理解产品或品牌信息 |
| 平台探索型 `exploration` | 淘宝、Booking 搜索结果、Spotify 或 YouTube 首页 | 发现、筛选、比较内容或对象 |
| 任务系统型 `task_system` | Dashboard、GitHub、控制台、钉钉文档、CI/CD | 诊断、执行、编辑、协作与状态闭环 |

示例用于帮助理解，不将品牌名当作固定分类：同一产品的不同页面可承担不同任务。三个候选都明显时也不自动录入三个范式，说明范围较混杂，让用户选本次最关注的两种或明确缩小评估范围，不静默丢掉核心任务。

确认问题同时呈现推荐比例、判断依据、上述三类示例和可调整选项。例如：

> 本次希望按什么页面定位评估？页面包含筛选比较和资源操作，我建议平台探索型60%＋任务系统型40%。两种定位接近，请确认本次侧重。展示叙事型常见于营销落地页、AirPods产品官网、公司官网；平台探索型常见于淘宝、Booking搜索结果、Spotify或YouTube首页；任务系统型常见于Dashboard、GitHub、控制台、钉钉文档、CI/CD。
> 可接受推荐、仅按平台探索型、仅按任务系统型，也可直接输入其他范式或比例。

有文本交互提问工具时使用工具，将推荐方案放首位；提供“推荐混合 / 仅主范式 / 仅辅助范式”三个选项，自由输入用于自定义调整。单范式推荐同样允许用户增加辅助范式或更换范式。工具不可用时用普通问题等待答复。不要把推荐的预选状态当成用户已提交。

- 任意比例都默认确认；主辅相差不超过20个百分点时（包含60%/40%、50%/50%），特别说明定位接近。此阈值只影响解释，不改变分数。
- 用户已明确指定单范式，则按100%采用；已明确指定主辅及比例，则直接采用。仅提到两类但没有比例，仍须给出推荐并确认。
- 用户明确将分类和赋权交给agent决定、要求不再询问时，遵循其授权，记录真实委托原话和模型采用的配置，不假装比例由用户逐项指定。
- 用户答复“就按推荐”可记录为确认，并把当时完整推荐方案一并保留在 user_statement 中。不能用产品截图、页面文本或模型推断冒充用户答复。
- 等待期间可以整理只读预览和任务清单；不进行依赖该选择的正式评估或生成场景分。等待超时不能默认接受，也不能为绕过确认自动降为 baseline。
- 用户明确只需基准评估或关闭场景计分时用 baseline，无需范式确认。无 context 的旧计算输入保留 baseline 兼容入口；这是脚本能力，不是新评估绕过确认的理由。
- 两套一起评估且范围相同时共用一次确认。同范围复测沿用选择；输入范围或范式比例实质变化时重新确认，更新 context.id 并记录原因。

比例称为“评估权重”，不是模型分类置信度或线上使用频率。主范式份额至少等于辅助范式；仅一个范式时100%，两个时份额均大于0且合计100%，相等时主次仅用于展示顺序。不得看到扣分后改权重。

## 确认记录与任务拆解

在正式判定前冻结 context。`paradigm_selection` 是唯一范式配置，所有任务场景都继承它；不在 scenarios 内独立填写 paradigm 或 paradigm_mix。

```json
{
  "id": "review-context-r1",
  "frozen": true,
  "product_type": "运营控制台",
  "paradigm_selection": {
    "primary": {"paradigm": "exploration", "share": 0.6},
    "secondary": {"paradigm": "task_system", "share": 0.4},
    "confirmation": {
      "source": "user_reply",
      "user_statement": "示例用户答复：按平台探索型60%＋任务系统型40%评估。"
    }
  },
  "assumptions": ["任务默认等权，仅代表此次审查范围"],
  "scenarios": [
    {
      "id": "S1", "task_id": "T1",
      "goal": "识别异常资源并比较原因",
      "basis": "用户要求诊断；页面存在筛选、指标与资源列表",
      "primary_task": "diagnose", "secondary_tasks": ["compare"]
    },
    {
      "id": "S2", "task_id": "T2",
      "goal": "对选定资源执行变更",
      "basis": "用户指定的核心任务与可见变更入口",
      "primary_task": "execute", "secondary_tasks": []
    }
  ]
}
```

confirmation.source 可为 explicit_input（用户最初明确指定）、user_reply（用户确认回复）或 delegated（用户明确委托agent决定、不再询问）。user_statement 必须记录实际用户选择或委托及其对应配置。代码只校验结构，不能证明用户实际说过这些话；不得复制合成样例作为真实用户确认。

任务类型：discover（发现）、compare（比较）、consume（阅读/消费）、diagnose（诊断）、execute（执行）、create（创建）、collaborate（协作）、decide（决策）。每个场景一个主任务及必要辅助任务；主辅任务对已评审任务标签的命中目前同等处理，多次命中只加一次。

可选字段：

- user_profile、input_capability、risk_capabilities 与场景 role 用于记录用户、证据能力与语境，不直接增加乘数。
- task_shares：按 task_id 指定正数份额、合计1，默认任务等权。同任务的多个场景平分任务份额。任务份额与主辅范式比例是两套独立概念，不把60%/40%的范式比例再复制为任务份额。
- criterion_scenarios：例如 {"A01.02":["S1"]}，在检查前指定条目所对应的实际任务场景，未列出的默认关联全部场景；不决定适用性，不能因标签未命中而记N/A。

## 标签来源与边界

`scenario-tags.json` 只收录当前 canon 的最终检查项。主准则、基础重要性与适用性以当前 canon 为准；评审标签只提供场景相关性。删除或合并前的旧条目不恢复。

`paradigms` 的已评审 1/2/3 作为弱/中/强相关性；不直接解释成三倍损失。`task_scope` 只有完成评审且为 task_specific 的映射才产生任务加权。

本批 `tasks` 数值全部为 1，暂不用于区分任务；`stages` 为空，不赋予阶段权重。标签评审的 confidence 不等于产品证据置信度，不参与分数。未完成标签字段按中性贡献处理，同时报告 `neutral_fallback`。

易用性的 F1.02、F7.03 未完成标签评审，保留当前 canon 的重要性，场景系数回退 1。一致性 B04.15 未指定 task_scope，仅取消任务加成，范式标签仍有效。上述说明分别按本包是否包含该条目适用。

标签中的 conditional、自然语言评论不能覆盖当前 canon 的适用条件；例如“未标条件”不意味着永远适用。审查时仍按真实触发器判断适用、不适用与证据不足。

## 四条控制通道

1. 适用性：使用 canon 和当前任务事实，场景弱相关或未命中任务均不等于 N/A。
2. 检查优先级：核心风险义务 → 核心任务依赖 → 基础重要性 → 场景相关性 → 证据缺口。标准模式仍检查全部适用项。
3. 场景计分：按下述有限幅度系数调整，不改写准则判断。
4. 建议严重级别：由条目重要性与实际缺陷程度决定，用于整改排序；不设置 Gate、风险封顶或自动发布裁决。风险能力仍用于安排取证，不自动证明存在缺陷。

## 确定性系数

参数仅从随包版本化的 `scenario-policy.json` 读取，不能由模型在报告层随意赋值。

```text
m_is = clip(0.85, 1.25,
  1 + 0.15 × Σp[用户确认的主辅范式份额 × (已评审相关性 − 2)]
    + 0.10 × 是否命中已评审主要任务)
```

缺失或未评审字段对增减项贡献为 0。universal 和未命中任务均无任务加成。系数为弱相关约 0.85，中性 1，强相关 1.15，任务匹配最高加至 1.25。这是试行策略，尚未完成样本标定。

先用同一份主辅比例混合每条准则的范式相关性，再按各实际任务场景判定任务加成，最后限制系数范围。不是先给两种范式各打一套总分后平均，也不是在主辅范式之间取最大值。

对一条准则，aggregate_multiplier 是其已冻结任务场景中的任务份额加权平均，用于一致性计分。对独立易用性问题，先完成主辅范式混合，再按其实际影响的准则/任务场景组合取最大系数，仍只扣一次。因此辅助范式参与每个候选系数，跨任务取最大值不会将它移除。

例如A01.02在探索型的相关度为2、任务系统型为3，确认60%/40%后，范式系数为1+0.15×[0.6×(2−2)+0.4×(3−2)]=1.06。诊断/比较任务命中后为1.16，执行任务未命中为1.06。一个Major问题影响两种任务时，场景扣分为1.5×max(1.16,1.06)=1.74，而非按主辅两种范式分别扣分。

生成权重：

```bash
node scripts/scenario_profile.mjs context.json > scenario-profile.json
# 也接受包含 context 的 assessment；包内有可执行计算样例
node scripts/scenario_profile.mjs references/scenario-example.json > example-profile.json
```

输出包含每条权重的范式分量、任务命中、中性回退和 `profile_id`。profile_id 绑定上下文、标签和策略内容，用于复测追溯。权重脚本只计算场景配置，不执行页面取证，也不判定产品质量。

## 计分模式与可拆分边界

`scoring_mode` 仅支持：

- `dual`：新评估在主辅范式与比例确认后默认使用。同一份判断与问题计算基准分、场景参考分及差值。
- `baseline`：仅计算现有口径，用于用户明确只要基准分或关闭场景策略。兼容输入不带 context 时默认为 baseline；明确请求 dual 却缺 context 会报错。

用户选择已记录且上下文已冻结时，执行者应明确写 `scoring_mode: "dual"`，把 context 放入既有 assessment 的同名新增顶层字段。不得由两次独立模型评估分别生成两个分数。

基准分用于现有质量评级；场景分显示“参考分（试行）”，不套用正式档位。两分均直接采用各自的汇总结果，不做风险封顶。基准证据门槛不满足时，场景分同样未评分；加权证据缺口超过 40% 时场景分单独未评分，不能放宽原门槛。

v2 的 dual 输入必须有 paradigm_selection 和确认来源；旧 context 需先确认并迁移，删除任务场景内的范式字段，不自动把旧比例视为用户确认。

新增脚本职责分开：paradigm_selection.mjs 只校验主辅配置及确认记录；`scenario_profile.mjs` 只读标签和 context；`scenario_scoring.mjs` 只做专项加权；`calculate_*_score.mjs` 编排基准与可选策略。现有取证/证据/导出协议继续独立运行。数字计算输入及专项公式见本包 `scoring-model.md`。

## 报告补充

在现有报告中补充：主辅范式名称/百分比/确认来源、实际场景与任务摘要、画像依据与假设、计分模式、基准分/场景参考分/差值、主要权重影响、未评审标签回退、profile_id 和策略版本。

`calculate_ease_of_use_score.mjs` 在dual模式输出 `scenario_impacts`，逐问题给出基础扣分、场景系数、场景扣分、扣分差值、全部贡献与实际驱动组合。报告直接读取该结构，不手工重算；最终分受维度0分截断、维度平均和舍入影响时，不得把单条原始扣分差值等同于最终总分差值。

场景差异只改变参考分，不能在报告层改写严重度或作自动发布裁决。报告和导出使用原有证据字段，不要求本轮迁移为统一证据结构。
