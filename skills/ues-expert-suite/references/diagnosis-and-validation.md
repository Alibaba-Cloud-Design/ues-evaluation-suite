# 发现与验证合同 0.1

本合同用于联合评估的开放诊断阶段。它帮助评估者发现逐条检查容易漏掉的任务错位、必要信息缺口和跨状态问题，但不新增评分标准，也不允许用场景权重代替缺陷证据。

## 何时读取

宽泛体验审查或完整 UES 联合评估在画像与路由之后、逐条准则判断之前完整读取。单专项独立运行时可选用；如果使用，仍服从该专项的证据与评分规则。

可运行网页若需要性能取证，必须先完成性能能力预检。正式计时导航开始后，可以让同一次任务执行同时产生诊断与专项证据；纯侦察不能冒充性能样本。

## 一、建立任务决策合同

对每个核心场景记录：

- `goal`：用户希望达成的结果；
- `decision`：用户必须作出的判断；纯阅读任务可写需要形成的理解；
- `required_information`：作出判断必须同时获得的信息与状态；
- `success_outcome`：用户如何确认目标已经完成；
- `basis`：用户陈述、产品材料、可见界面或其他可复核来源；
- `assumptions`：仍未证实的业务假设。

不得仅凭页面类型编造工作方式。缺少会改变主要判断的信息时，先记录缺口；不依赖该缺口的观察可以继续。

## 二、开放诊断

先观察材料或执行一次核心任务，不按准则顺序逐格填写。寻找三类候选：

1. **任务错位**：界面让用户执行了动作，却没有提供作出正确决定所需的信息，或操作成功不代表业务目标已经完成。
2. **情境失效**：中断、返回、相似对象、外部变更、错误恢复或跨角色交接时，正常路径依赖的假设不再成立。
3. **第一印象误判**：看似拥挤、冗余或不一致的设计可能服务于比较、专家效率或风险区分；先检查合理解释，再决定是否提出整改。

每个候选至少写明 `observation`、`hypothesis`、`potential_consequence` 和关联场景。观察只写已见事实；假设与后果不能伪装成观察。

## 三、定向验证

每轮优先验证最多三个候选，然后重新排序。优先考虑：

1. 有依据且可能影响核心任务或造成较大后果；
2. 验证结果会改变是否报问题、严重度或整改方式；
3. 能在当前材料、权限和风险边界内取得区分性证据；
4. 场景相关性；它只用于调度，不能证明问题存在。

对候选记录：

- `action`：实际执行或检查了什么；
- `expected_discriminator`：什么结果支持或反驳假设；
- `evidence_ids`：共享证据索引中的原始证据；
- `alternatives_checked`：检查过的合理解释；
- `remaining_uncertainty`：仍不能排除的解释或范围；
- `status`：`confirmed | rejected | pending | blocked`。

`confirmed` 必须同时具备任务依据、可定位观察、验证证据和反证记录。静态材料无法验证的交互候选保持 `pending` 或 `blocked`，不能进入实证缺陷或扣分。`rejected` 候选保留简短依据，用于避免后续专项重新提出相同误报。

## 四、转入专项

- 确认候选映射到一个或多个专项时，每个准则关联仍需独立证明；诊断结论不自动产生 `fail`。
- 能确认是真实体验问题、但当前准则无法合法覆盖时，输出为不计分建议，并说明为什么不纳入分数。
- 专项查漏阶段继续检查所有适用且可验证条目；开放诊断不能替代覆盖要求。
- 专项可复用诊断中的证据 ID、任务合同和已排除解释，只补自己的证据缺口与判断依据。

## 五、停止与更新

必要覆盖已完成、关键判断已有证据、当前一轮没有新增高价值候选时停止扩展。不得为了显得深入而凑问题。

输入、任务合同或共享证据变化后，先判断哪些候选与专项结论受影响。只有受影响部分重新验证；报告文字变化不触发重新取证，判断变化必须重算相关分数和汇总。

## 六、产物与校验

联合评估保存 `diagnosis.json`，使用 `assets/contracts/diagnosis.example.json` 作为结构示例，并运行：

```bash
node scripts/validate_diagnosis.mjs /absolute/path/to/diagnosis.json
```

校验只证明结构和引用条件满足，不证明洞察正确。最终仍需人工式判断复核。
